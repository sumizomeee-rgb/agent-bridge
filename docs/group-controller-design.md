## 1. 产品目标与决策来源

目标是多个独立 Bot 在同一聊天平台同时运行，在群中自主交流、调查、交接并分别派执行助手；同一 Bot 的身份、能力、当前上下文和记忆从私聊延续到群中。

用户已明确的规则：

- Bot 的身份与启动独立于聊天用户；同一平台可以同时启动多个 Bot。
- 私聊准备过的 Bot 进入工作群后应能继续；没有主控会话的 Bot 仅被拉进群不会启动主控。
- 同一 Bot 的私聊与工作群共用主控上下文。用户已明确接受：群 `/new` 重置相关 Bot 时，也重置它们私聊正在使用的上下文，取消旧定时并停止已启动的定时助手。
- 群 `/new` 可以初始化或重置本群的全部桥 Bot，而不只是收到该命令的一个 Bot。
- 群由首个满足白名单条件并成功激活的用户控制，普通群员及其他白名单群员的输入不触发工作。
- Bot 之间能接收协作消息；群的命令清单应比私聊少。
- Bot 默认具备通用能力，不要求预设“日程／工作／风险审查”等固定职责。用户可以自定义偏好，具体分工随任务形成。
- 群聊提供共同工作现场，让各 Bot 自主决定补充、质疑、调查、接手、交接或保持安静；私聊和群聊的沟通方式由 Agent 结合现场判断。
- 不做旧语义兼容层；改动现有数据语义时，应有完整、可检查的一次性迁移。

本轮选择的首版方案（不是声称用户逐项确认了接口拼写）：

- **一个 Bot、一个当前主控、一个激活用户。** 多个白名单用户可分别使用不同 Bot，同一个 Bot 不并行维护多名用户的当前主控。
- **支持同一 Bot 参与多个工作群。** 用户将首版范围的权衡交给实现者；采用共享上下文、逐事件固定回复地址的方式，不为每个群复制主控。
- 群激活与新建会话分开，暂定 `/group start` 与 `/new`。负责人的普通群输入向全体已激活、就绪成员各提供一次自主参与机会；真实提及、回复关系、正文姓名和别名都是理解内容的事实，不筛选收件主控。收件 Bot 负责平台入口及控制回执，不决定其他 Bot 是否有资格参与。
- 保持现有重任务委派方式。主控是否增加直接查询、记忆读写或 Bash 权限，是独立议题，不作为本功能的前提。

## 2. 首版范围与当前缺口

支持：同平台多 Bot、私聊与多个工作群续用主控、单操作者权限、群命令、定向协作与任务交接、重启恢复。飞书与 Discord 共用领域规则和命令语义，适配器处理身份、收件、菜单、提及和排版。

不纳入：同一 Bot 的多用户独立会话、在线转移主人、跨平台同一主控、陌生 Bot 联邦、无界自动互唤、群语音、自动跨群转发、严格的同一 Bot 跨入口信息隔离、为本功能直接开放主控 Bash。

| 当前代码事实 | 开发时必须改变的地方 |
| --- | --- |
| `src/main.ts`、`src/instance-lock.ts`：同一项目只运行一个所选 Profile | 一个宿主管理同平台多个 BotRuntime；继续防止同一真实 Bot 重复登录 |
| `src/manager.ts`、`src/store.ts`：当前会话、运行队列等大量按 userId 索引 | 身份与当前主控按 botId 索引；userId 只参与认证及操作者映射 |
| `src/feishu.ts`：仅接收白名单用户 p2p；`src/discord.ts`：排除 guild 和 bot 作者 | 接入群入口；已激活群的可见发言与执行授权分开，非负责人发言只作现场，内部协作独立于平台 Bot 回流 |
| `src/slash.ts`：仅 BOT_DM；`src/commands.ts`：一份共用命令表 | 命令增加允许的场所、目标范围及所有者要求，避免两个平台维护两套行为 |
| `src/controller/native.ts`：只有桥管理工具；`src/controller/runtime.ts`：助手归原主控 | 增加长期 Bot 协作能力声明，保持执行助手与长期主控两个层级 |
| `src/ingress.ts`、`src/restart.ts`、`src/lifecycle.ts`：已有持久收件、排空和恢复 | 扩展为宿主级控制与 Bot 级队列，不能在重启时重新认领用户或初始化 Bot |

## 3. 领域对象与不可变规则

| 对象 | 稳定身份与职责 |
| --- | --- |
| Bot | `botId = platform + verifiedApplicationId`。Profile 别名、显示名或密钥变化不改变身份；称呼由该 Bot 私有 Profile 的 `aliases` 数组登记 |
| Principal | 桥内操作者身份，映射各应用下的真实平台用户 ID；不是显示名 |
| Controller | 一个 Bot 的当前原生主控会话；保存 conversationId、nativeId、generation、模型与强度 |
| Space | 一个飞书群或 Discord 频道／话题；Discord 服务器只是上层容器 |
| GroupBinding | Space 的负责人、收件 Bot（平台入口）、明确的成员 Bot 集合、绑定 epoch、成员 revision 及启用状态 |
| Event | 原始来源、操作者、目标 Bot、原会话代次、固定回复地址、可见范围、因果链及幂等 ID |
| Work / Handoff | 任务身份、当前负责 Bot、授权来源、交接状态和结果；执行助手仍归具体主控会话 |

约束：

1. Bot 的 ownerPrincipalId 在首次有效初始化时确定；`/new` 不释放或改变主人。可预配置主人，首次输入必须匹配。
2. 激活用户是当前主控的控制者，不是 Bot 身份的组成部分；改用户名、群名或 Profile 名不影响既有会话。
3. 一个工作群只有一个负责人；成员 Bot 必须属于该负责人，或尚未初始化且可由其合法激活。其他人拥有的 Bot 不纳入本群。
4. 一个 Bot 可以关联多个群，但同一原生主控一次只运行一轮；不同 Bot 可以并行。
5. 所有私聊、群、助手结果、协作和定时事件进入同一个 Bot 队列。不能继续按“一个用户一条队列”串行所有 Bot。
6. 一轮的回复地址在收件时确定。后来的私聊、另一个群的消息或“最后联系用户”不能覆盖它。
7. 同一 Bot 在所有入口共用当前 generation。群 G1 重置 Bot A，A 在私聊和 G2 也会续用新会话；没有涉及的 Bot 不重置。
8. 共享上下文不代表程序会复制私聊记录到群，但也不提供严格的信息隔离。需要隔离记忆或保密边界的工作，应使用不同 Bot。
9. 首版主人不在线转移。其他白名单用户不能通过私聊 `/new`、群激活、修改显示名或移除群成员来抢占。
10. 白名单撤销后立即拒绝该人的新输入，并暂停其群入口；不自动把已有上下文交给下一名白名单用户。新 Bot 的身份、权限映射及启动成员仍在启动前配置。

## 4. 身份、启动和上下文

宿主按启动配置加载一组同平台 Profile。一个 Profile 对应一个真实 Bot。连接平台、拥有主控、参加工作群是三个独立状态：

- 平台连接就绪不自动新建主控；没有会话的 Bot 只接收必要的管理和初始化指令。
- 私聊保留现有体验：`/new`，或首次合法普通输入产生的自动新建，均建立该 Bot 的主控并绑定操作者。
- 私聊里设置的模型、强度、偏好和当前上下文，随同一 Bot 进入群；不会因群激活而换模型、降低能力或强制指定职责。
- 目标语义中，Agent／模型／强度选择属于 Bot 的持久设置；`/new` 重建工作会话并沿用这些选择，只有显式设置 `default` 才恢复相应默认。实际模型回报仍单独记录。若现有私聊实现与此不同，应在本次语义迁移中明确调整并验收，不能以群激活为名偷偷改值。
- 各 Bot 使用独立的上下文工作区，沿用 `README.md / MEMORY.md` 加当前平台指南的约定；共用知识由明确链接引入，不复制其他 Bot 的全部记忆。
- Bot 的上下文工作区与执行任务的 workingCwd 分开；私聊 `/cwd` 调整工作目录时，不能把身份、主人或 MEMORY 写到另一个 Bot 的目录。
- 各执行 Agent 继续使用所在电脑已有的 CLI、网关、技能及认证。用户自定义模型别名不需要因官方模型名不一致而受质疑。
- 启动集合、身份映射、凭据和网络预设不通过群聊修改。每个 Bot 的代理设置独立，不能把 Discord 的代理隐式套给飞书。
- 下线某个 Profile 不等于注销它的身份或删除会话；其他 Bot 不应受影响。

目标配置可采用 `startupProfiles` 数组（单 Bot 也是一个元素），而不是为了多 Bot 同时运行多个竞争同一项目锁的旧启动脚本。字段名称可在实施时细化，语义必须一致。

### 私聊续接与 Agent 切换

- 一个 Bot 只有一个当前主控，且只服务一个已激活的平台账号；权限按已验证的 Principal 判断，当前会话、队列和交接来源按真实 botId 归属，不能只按 userId、目录或后端查找最近会话。
- bot1 私聊 `/new continue` 先冻结 bot1 当前主控的会话和代次，交接其已经获得的上下文，包括它在私聊和各群获知的内容；不读取 bot2 私有上下文。没有当前源会话则明确提示，不回退到其他 Bot 或目标后端的旧会话。
- `/new [continue] [codex|claude]` 的 continue 决定是否提炼上述源会话，agent 决定新会话运行后端，二者独立。两种 new 都取消旧定时并停止已启动的定时助手，普通旧助手不自动转移归属。
- `/agent` 无参数只查询；选择当前后端保持原生会话、不提炼、不初始化。真正切换后端时，内置当前上下文摘要交接，目标后端新建会话；Codex → Claude → Codex 始终从此刻最新主控向前交接，不恢复某个后端过去的分支。
- Agent 切换只复用摘要交接能力，不照搬 new 的取消生命周期。等待当前轮安全结束，成功准备目标后才提交当前后端及原生会话；失败保留旧主控。保持逻辑 Bot、操作者、工作区、群绑定、普通助手和定时计划的归属，不重复执行。后端会话切换与旧代次事件／预约重绑须有操作日志及崩溃恢复证明，不能只替换 nativeId。
- 目标后端使用该 Bot 对应后端保存的模型／强度选择；首次使用沿用目标后端默认，不复制不兼容强度。原生 ID 可以变化，摘要交接不冒充完整原生续接。

### 按平台读取操作能力

初始化由 README 引导，初始化助手按桥提供的平台只读 `chat-platforms/lark.md` 或 `chat-platforms/discord.md`；主控只接收能力概括：能做什么、何时委派、执行者应读取的文档路径和未知边界。完整平台指南、接口参数、命令示例与技能步骤留给执行 Agent 按任务读取，不全文注入主控。普通初始化概括目标800–1500个Unicode字符，信息少不凑字；保留用户偏好、授权边界、目录职责、相关机器别名与权威入口，合并重复细节，不以截断丢弃规则。`/new continue` 与真实 `/agent` 切换沿用工作区摘要不超过1000字符、历史续接摘要不超过3000字符及合计14KiB的独立预算；续接信息不挤进平台能力说明。不初始化其他平台、不读取凭据或做网络探测。当前 Bot 的固定身份和实际能力与共享指南分开，显示名变更不迁移 Bot 身份。API 能满足已授权需求且可核对结果时优先考虑接口，由已有工具或执行 Agent 完成；文档不是新增工具、权限或群功能开关。

此前精简主控固定协议说明时，工具参数契约保持不变（以下为该次历史计量，本轮新增协作工具不沿用此数量）：固定指令从9624降至4275字符，28个工具的JSON声明从19971降至16298字符；合计29595→20573，减少9022字符，约30.5%。此计量仅含固定协议，不含初始化概括、聊天现场和历史，也不是token计数。

浏览器故障与正常重启经验分层维护：README 只保存结果核验原则和平台文档入口；`chat-platforms/lark.md` 保存执行助手按需读取的进程、连接和网页验收步骤，初始化不回传完整流程，不新增 Markdown 文件。

`/new continue` 的摘要目标留出余量：工作区概括600–800、历史续接1200–1800个Unicode字符，硬上限仍为1000／3000及合计14KiB。仅正常完成而格式或预算不合规的初始化回执，允许同一已登记助手、原生会话和任务内压缩修复一次，不扩展读取或执行范围，不直接截断约束。修复机会先持久登记；来源哈希／归属错误、取消、重置或未知执行结果不自动重做，修复中断后也不重放。再次不合规时保留实际字段长度等具体错误，统一提示初始化未完成，不能把摘要验收失败说成文件读取失败。已失败交接可通过受支持的显式续接重试保留原冻结来源，不手改就绪标记。

### 工作区原则与运行时现场

工作区 Markdown 骨架为 2 + 平台数：README 统一保存导航与持久原则，MEMORY 积累用户稳定偏好和已核实的经验；补充的聊天平台指南按 README 明确入口读取。Agent 特有的工具提示仍放在各自用户级上下文。以下短段作为共享 README 的建议内容，实施时再落入个人工作区：

> 根据当前对话的参与者、消息可见范围和最新进展，自主选择沟通与协作方式。职责随具体事情形成，可以主动补充观点、开展调查、请求协助或交接工作；接手后负责推进并交付。结合其他参与者的进展作出贡献，群聊没有新增价值时可以保持安静，私聊真人输入仍需回复。

Bot 别名只在各自现有私有 Profile JSON 的 `aliases` 数组登记，不另建身份 Markdown；桥在私聊运行事实、初始化事实和群参与者现场中提供本人及已验证成员的称呼。别名不分配职业、人格或固定分工，不改变 owner、真实身份或权限。自然语言称呼和真实平台提及均交由模型结合现场理解，不作为普通群输入的收件过滤，不强制派工或要求必答。

桥为当前消息提供简短、结构化的信封：实际发言者与身份，真人输入／公开观察／内部咨询／任务交接的事件性质，当前消息的来源与可见范围，以及分开记录的原始主人授权和默认交付地址。内部咨询不能因授权来自群而被标成默认公开回复群。负责人的普通群输入另附本条直接投递的 Bot 身份列表，只表示桥已登记的收件事实，不代表已读、接受或完成；动态主控状态清单仍按需查询，不逐轮注入。近期公共现场只保留有界、去重的必要进展，不重复当前原话和原始授权；较早内容按需查询历史。运行前刷新现场，忙碌事件合并排队，不能假称模型已经看过尚未消费的消息。

私聊与群聊使用相同的主控能力和授权原则；交流长度、跟进时机及是否接手由模型判断。群聊收到消息只表示获得一次参与机会，各 Bot 自行决定回复、补充或静默；私聊的真人输入必须交付回复，不能用静默结束代替回复。桥不指定永久主持人、强制讨论轮数、固定口吻或群里每句必回，也不要求先获得全体共识才能调查。模型可按授权选择当前群公开回复、提及某个成员、桥内定向协作或单独私聊；工具声明必须说明各动作的真实受众。当前参与者和聊天地址不写入持久原则；稳定偏好经核实后才进入 MEMORY。

### 消息可见性、默认注入与按需历史

- 已激活群的可见发言不按执行白名单过滤。负责人身份、执行白名单和群权限控制命令、派工及副作用；其他已核验群成员的发言单独登记为只读现场，保留真实发言者、消息时间、来源、提及和回复关系，不伪装成负责人的输入，不创建授权根任务。
- 默认只有负责人的合法输入与已有授权的协作事件触发主控；旁观发言不逐条调用模型。它们进入近期／未读现场，供下一合法轮理解讨论。成员说“/new”或“请执行”仍只是资料。平台 Bot 回流不产生重复授权或无限互唤。
- 同一 Bot 的私聊、各激活群和后台事件沿用同一原生主控。每条输入都附真实来源；每次群轮自动附有界近期／未确认递交的群现场及成员称呼、任务状态；私聊轮也附本人激活群的有界现场（总计最多 40 条），保留各群来源，不能自动公开到其他群，不要求用户提醒“先查现场”。来源与受众不从最后联系人或模型文本猜测；合批、忙碌补充和重启恢复也保留原来源。
- 未确认字段只表示桥没有记录递交确认，不声称模型语义上已读。注入和历史查询的文本均有条数／长度上限，截断、未读范围与缺失必须明确标记，不能声称已看完整群史。历史、引用、旁观成员和 Bot 发言是证据，不因进入上下文获得新授权。
- 主控通过 `bridge_read_group_history` 按需读取真实平台群历史。群轮省略目标时使用当前群；私聊须先查询可投递区域并明确选择已激活群。支持时间范围、每页上限 50 条和受绑定约束的分页游标，返回发言者、时间、正文、提及／回复、附件描述和实际覆盖范围；不自动下载附件、不把读到的历史重新派工。
- 历史查询前后重验本人权限、Bot 和负责人在群状态、群 epoch/revision 及主控代次；游标绑定 Bot、负责人、群、过滤条件与绑定版本，不能用于其他群或新代次。飞书与 Discord 以各自真实接口返回为准，权限不足／内容不可读要如实说明。

## 5. 群激活、成员和退出

### 首次激活

未激活的群不把普通消息送给模型。用户需通过明确点名某个桥 Bot 的文本指令，或选择该应用的原生指令入口，提交 `/group start` 或 `/new`，避免多个 Bot 同时抢答。

`/group start`：

1. 验证调用者为有效白名单用户、确实在群中，并满足所有目标 Bot 的身份映射与控制权要求。
2. 冻结本次明确、可核实的候选成员集合，持久登记负责人；并发认领由宿主事务裁决，先成功者生效。
3. 以被点名／被选择应用的已初始化 Bot 为收件 Bot。它必须能读取本群所需消息；不满足则拒绝并说明缺项，不随机选另一个。收件身份不赋予任务审批权或唯一发言权。
4. 接续候选中已经属于该操作者的主控。未初始化者标为“未初始化”，不为其调用模型。
5. 发一次简短回执，列出负责人、收件 Bot、参与 Bot 与未就绪项。声明“激活成功”必须与实际持久状态一致。

`/new` 可在未激活群中完成认领并批量初始化，详见第 8 节；此时不要求收件 Bot 预先有主控。

### 成员变化

- 群成员集合不是“群里所有机器人”：只包含本宿主登记、确认在群中、符合当前负责人权限的桥 Bot。
- 显示名或模型文本中的“@某 Bot”不能证明真实身份；使用平台的提及实体和配置中的真实 Bot 身份。
- 新 Bot 入群不自动加入工作集合。负责人再次 `/group start` 刷新成员并接续已初始化者；群 `/new` 则初始化／重置刷新后的集合。
- 不能把未知在群状态当作已加入；回执报告未纳入项。已登记成员暂时离线不能在批量操作中被静默跳过。
- “全部”始终指本群明确登记的成员快照；不属于当前操作者的 Bot 要在回执中列为未纳入，不得借群命令接管。
- 未登记的外部机器人、Webhook 和普通群员都不成为协作主体。
- 收件 Bot 离线时保留已接收任务，群普通输入能力标记受限；负责人可点名就绪成员执行 `/group start` 更换入口。这不改变任何 Bot 的模型、任务身份或能力。
- 完全相同的 start 不改变版本；成员／收件 Bot 更新只增加 revision，并复核相关权限，不取消无关的原任务。停用后重新激活才产生新 epoch，旧 epoch 不自动恢复投递。
- 群负责人退出／失去访问权时暂停整个绑定，不自动让第二个白名单用户继承；Bot 私聊和其他群仍可继续。

### 停用群

`/group stop` 停止本群的新输入、协作唤醒及公开投递，保留 Bot 的主控和长期记忆。它不等于 `/stop`：

- 已获授权的执行任务与计划保留；结果存回原任务记录，不在停用群中发送，也不自动改投另一个群或私聊。
- 正在发送的请求只能记录实际送达状态，不能承诺撤回已发生的投递；停用后不再发新的普通回复。
- 已排队但未启动的本群普通输入与协作事件取消；其他入口的队列不受影响。
- 已启动的协作工作继续归当前负责 Bot；向停用群的回送标记为“目的地不可用”，不得无限重试。
- 需要停止工作的用户应先使用 `/stop`。重复停用幂等；重新激活产生新绑定版本，不自动重放停用期间的消息。
- Bot 被移出某群时只撤销它在该群的绑定；它在其他群的工作不会被顺带停掉。

## 6. 群命令与普通消息路由

命令仍来自同一份注册表；增加场所、目标和权限元数据，由平台渲染菜单。下表是首版目标语义，名称尚未发布。

| 命令／输入 | 范围与行为 |
| --- | --- |
| `/group start` | 认领或刷新当前工作群，接续已有主控，选择接收指令的 Bot 为收件入口；重复调用不重置上下文 |
| `/group stop` | 停用当前群绑定，不重置主控、不停止其他入口 |
| `/status` | 汇总本群成员、负责人、收件 Bot、初始化及连接状态，不创建主控 |
| `/workers [history] [all] [details]` | 复用私聊的助手查询及结构化展示，由各 Bot 用自己身份分别回复；默认查询该 Bot 当前主控，不拼接群任务登记。无真实提及时查询本群全部成员，真实提及时只查指定成员；静默协作助手不公开 |
| `/new` | 初始化／重置本群全部明确成员；影响这些 Bot 的所有入口，并取消旧定时 |
| `/stop` | 停止本群成员 Bot 当前受桥管理的主控／助手工作和预约，清空其共享会话队列；会影响私聊和其他群，回执必须说明 |
| `/help` | 仅列当前场所允许的命令，并解释群命令范围 |
| 负责人的普通群消息（含真实 @、回复或正文称呼） | 向全体已激活、就绪成员各提交一次参与事件；名字与提及保留为内容事实，各主控独立选择回应、工作或静默，不等待固定主持人批准 |
| 其他人／未知 Bot 的消息 | 不触发模型、下载附件、派工或记忆写入 |

补充规则：

- 群 `/new` 和 `/stop` 是全体命令；Discord 菜单选择哪个应用只决定收件入口，不把范围缩成该应用。
- 首版不提供群 `/new continue`、模型／强度切换、目录切换、Agent 切换和宿主重启；在目标 Bot 私聊中操作。参数不支持时明确报用法，不忽略参数后执行。
- 群与私聊 `/workers` 共用参数校验、当前／全部主控查询、活跃／历史筛选和卡片生成；群不再按 originatingSpaceId 截取普通助手。每个 Bot 只查询自己负责人的助手，不混成全桥清单；群不展示静默内部协作助手或私聊主控标题。查询不调用模型、不初始化未就绪主控、不改变任务归属；查询后发送前重验成员、主人、绑定及主控代次。群任务认领／交接记录仍由主控工具查询，不混入助手命令。
- 私聊 `/new` 只重置目标 Bot，但因为上下文共享，它所在的各群也续用新会话。
- 同一条负责人普通群输入只有一个授权根请求，全体已激活、就绪成员各参与一次；提及多少成员都不改变该范围。任务登记与接手仍去重，不能把同一任务复制成无关联的多份。控制命令继续按其明确的入口、范围和鉴权处理，不套用普通消息广播。
- 原生菜单不可见不能替代桥自身的权限检查。负责人之外的人即使绕过菜单发文本指令，也不会执行。

## 7. 群记录、回复地址和 Bot 互通

### 共享记录与固定来源

宿主持久保存已授权的群输入及桥 Bot 的群发言。成员 Bot 在参与轮次中可读取有界的最新公共记录，保留各自的私聊、模型选择和长期记忆。群公共记录仅包含实际公开的信息；桥内定向协作不自动广播。

事件至少携带：eventId、rootRequestId、causeEventId、principalId、sourceBotId、targetBotId、spaceId、bindingEpoch、membershipRevision、conversationId、generation、replyTarget、授权任务引用及附件引用。

- 默认回复固定回原入口：私聊回原私聊，G1 回 G1。主控通过 `bridge_delivery_targets` 查询当前 Bot 可发送的本人私聊和已激活工作群；统一的 `bridge_send_message` 必须选目标，默认作为最终投递并封闭本轮；显式 `finish: false` 才补充发送并保持本轮开放。`bridge_send_user` 保留原入口最终回复兼容用法，也可选显式目标；旧 `bridge_send_private` 仅向当前群轮次已验证负责人投递，同样默认最终发送、显式 `finish: false` 才补充，复用统一投递链且不要求在原群重复回复。查询和发送各自验权，群目标绑定 epoch/revision，变化后旧目标拒绝。输入来源、实际发送目标和任务原交付地址分开保存；跨区域发送不改任务归属或未来默认入口，不使用“最后联系的群／用户”选目标。
- 助手结果、定时计划和后续追问继承原任务来源；交接任务也保留原交付目的地。不能因为执行 Bot 最近在 G2 聊天，就把 G1 的结果送去 G2。
- 定时自唤醒不创造新的用户授权；工作群停用／失权时按“结果留存”规则处理，不自动换目的地。
- 普通群员及其他白名单用户的可见发言进入有界只读现场，不逐条启动主控，不成为新的执行授权；保留实际发言者，不能冒充负责人。
- 共用原生上下文会让同一 Bot 知道多个入口的信息；程序保证来源与投递绑定，不承诺模型层面的严格保密隔离。
- 不自动把整份私聊记录、个人 MEMORY 或助手完整日志贴到群里；显式附件仍需实际授权、文件范围及大小检查。
- 群内 @B 仍对全群可见；桥内定向协作仅所列目标可见；用户私聊需要真实可投递且已授权的目标。发送前向模型声明受众，不能把“点名”误当成“仅此人可见”。
- Bot A 下载的附件通过带来源和权限的桥内引用分享给 B；B 发图／文件时使用自己的平台凭据重新上传，不复用另一应用的资源 key。
- 主控通过发送工具的 `attachmentPaths` 明确交付任务产物；正文中的绝对路径、Markdown 或源码引用不自动上传。桥将 PNG/JPEG/WebP/GIF 路径经内容校验后交给平台图片出口，其他文件交给文件出口；路径须为桥电脑可读取的物理文件，继续执行既有大小、数量及读取检查。执行助手返回产物路径与用途，主控按任务选取必要图片／文件并简短说明，不将内部证据路径当成交付。直接执行模式既有 Markdown 回传规则保持。

### 后台 Bot 通信开关

公共配置新增 `internalBotCommunicationEnabled`，只接受布尔值。缺省 `true` 保持已有部署行为；公共示例显式为 `false`，新部署先以群公开协作为常态。配置在宿主启动时加载，修改后安全重启续接原生会话即可生效，不要求 `/new`。它控制 Bot 之间的后台通道，与群里的“已看到但不回复”是两项独立能力。

- `true`：开放本节下述内部定向咨询、内部模式发起及依赖内部通知的交接，仍受既有主人、成员、代次、授权根和预算校验。
- `false`：桥端拒绝 `bridge_send_bot`、`bridge_start_collaboration` 的 `internal` 模式、`bridge_propose_handoff` 与 `bridge_accept_handoff`。现有交接协议依赖内部通知，不偷偷替换成公开消息；不自动公开任何内部正文。
- 关闭不影响公开 `bridge_start_collaboration`、群公共消息广播、群 `bridge_silent`、本人私聊、程序维护的任务登记，以及各 Bot 的直属执行助手和正常结果交付。Bot 仍能在已授权群里公开讨论；不把已有主人消息再次递话当成协作前提。
- 新提供的工具清单隐藏内部接口，公开发起工具只声明 `public` 模式；旧原生会话即使缓存旧声明，实际调用仍被桥端拒绝。Codex 的旧清单可能继续可见，不能以界面缓存代替服务端判定，不为此强制重置会话。
- 已登记但尚未派送的内部定向咨询／交接事件不再送入主控；同时将尚未接受的 `proposed` 交接提议取消，解除其对原负责人后续派工的阻挡，再次开启也不复活旧提议。这里只取消提议，不取消任务或直属助手、不改变任务负责人或资源归属，不伪造交接完成；关闭不能撤回已经进入原生上下文的内容。
- 内部任务的助手结果与定时唤醒继续遵守原有内部可见边界；关闭通信后遇到失败也不得向群公开结果、错误正文或任务标题，不能以异常通知绕过开关。普通助手与其他已授权结果仍按原交付边界处理。

以下关于内部通道的机制只在开关启用时适用；公开协作与群静默不回复的机制不受该开关影响。现有真机验收记录描述当时开启内部通道的行为，不证明关闭场景已经现场验收。

### 自主参与、静默与有界唤醒

接收平台消息、提供参与机会和公开发言是三个不同阶段。收件 Bot 负责取得一个权威输入，宿主去重后按参与规则投递；它不先替其他模型判断“谁值得发言”。

- 负责人的普通群输入向当前全体已激活、就绪成员各投递一次，不因真实提及、回复对象、正文姓名或别名过滤目标。无会话、未纳入或无权限的 Bot 不参与；未初始化 Bot 不因普通输入自动新建会话。控制命令保留独立路由和权限语义。
- 各 Bot 使用自己的主控模型，独立选择回复、管理动作、开展工作或群聊静默结束；不同 Bot 的独立推理和调查不互等。`bridge_silent` 在群聊参与及允许的后台协作回合中表示正常终态，无需发送占位消息；公开回复校验与重试逻辑识别静默成功，不能自动重试或要求补发。私聊真人输入不能用静默结束，仍需给主人交付回复。静默不表示未收件、已接手任务或退出群。
- 原生控制层必须等待该模型轮次安全结束并释放占用。已经公开发布或静默结束后，不允许再派工；后续真正的新输入进入下一轮。公开送达、静默决定和原生轮次结束分别记录，不能混成同一个状态。
- 本根请求内的新公开发言向其他就绪成员提供后续观察机会；不只允许被点名者知道进展。明确提及、登记的咨询回答、交接和结果事件优先处理；自己的发言不回头唤醒自己。模型可选择不跟进，无需凑齐每个成员的回复。
- 同一个 Bot 忙碌时合并本根请求的未读进展，保存公共记录游标；不为每条发言堆积一轮过期推理。独立根请求保留各自来源，不因合并而串任务。控制命令优先，已接收的真实用户输入不会被 Bot 闲聊无限推迟。
- 互通由桥内部持久事件保证，不依赖平台转发 Bot 消息。公开提及与内部投递属于同一逻辑消息；平台回流仅补充送达证据，不再次唤醒。静默判断仍记录模型调用和耗时，但不增加群公开响应次数；只有内部定向协调或定时唤醒的适用轮次才计入独立根预算，不能用该预算截断普通群收件。
- 互通关联双方都参加、负责人一致且仍启用的工作群；私聊向群发言需明确选择已授权目的群，其他群的同名 Bot 不能成为目标。普通跨区域发言只写入目标群公开记录，不伪造成真人输入或自动唤醒成员；显式发起协作使用独立工具，私聊的真实主人授权也可建立绑定该共同群的协作现场，无需再让用户手动 @。内部定向消息只唤醒目标，不触发全群观察。
- `bridge_list_controllers` 只在主控需要时查询同一负责人的 Bot：返回稳定 ID、别名、共同激活群、初始化就绪状态、主控活动、待处理事件、执行助手数量和核查时间。可按精确 botId 筛选，limit 默认20、范围1–50，offset 非负。列表不加入初始化或每轮输入；没有当前证据则标未知，旧聊天或已登记不代表当前健康。发起协作时仍重新核对会话代次、主人、群状态和成员资格，不信任查询快照。
- `bridge_start_collaboration` 每次指定一个 targetBotId、来自 `bridge_delivery_targets` 的已激活群 targetId、`internal`／`public` 模式及必要 text；多人逐个调用。只能从真实负责人的当前输入发起，将原始来源、请求、主人及双方会话／成员代次持久绑定到协作现场，保留授权根、适用的内部协调预算和幂等约束；同一真实输入不能因重复调用、重试或切换目标群重建授权、补满内部预算。后台、定时或 Bot 消息不能借此创建新根，继续咨询使用已有现场的 `bridge_send_bot`。目标忙碌则排入其现有主控队列，不初始化或重置对方。
- `internal` 不公开咨询正文、内部任务标题或异常通知；后续公共群现场与群内助手列表过滤内部任务，通知必须重验原返回区域的绑定，失效不改投。收件方用 `bridge_send_bot` 回发起 Bot 后 `bridge_silent`，由发起 Bot 按原授权向主人汇总，不自动让收件方在群或私聊公开结果。`public` 仅在指定群发布显式 text，不复制完整私聊；平台确认送达后才为指定目标排队，未确认或结果未知不得盲目重发或声称已发起成功。若发起主控已在当前来源群公开发布所需内容，该公开送达可完成本轮交付，不强制再发“已递话”确认；从私聊或其他来源区域发起时，仍需在原入口完成必要确认。对方答复作为后续独立回合处理，不能因同群允许结束而取消异地输入的交付义务。授权不因公开文本扩大；后续内部定向协调／定时唤醒仍受独立根预算约束，公开回应则按每 Bot、每群的独立次数限制处理。
- 发起回执的 registered／queued 仅表示已登记／排队；已消费、已读、接受任务、完成和最终送达是独立事实。失败须报告没有发起成功，不能说正在等待对方回复；派发成功也不承诺对方一定公开发言或接受任务。
- Bot 发言保留真实来源，不能伪造人类授权，也不能直接执行 /new、/stop、认领群或修改白名单。群公开消息由实际发言 Bot 发出；工具操作默认静默，选择公开发布后按现有封闭协议结束本轮。
- 群公开响应采用每 Bot、每群独立的连续计数，上限 8 次。只在非主人回合的群公开消息获得平台 ACK 后计数，同一逻辑响应的多段消息或附件只计一次，失败／未知发送不能冒充 ACK。静默、不发言的模型轮次、收件与历史读取均不计数；达到上限只暂停该 Bot 对该群的这类公开回复，不停止其接收、阅读或模型参与，也不要求程序发失败通知或占位消息。主人输入轮的回复、私聊、执行助手结果与定时／内部交付不受此公开计数限制。
- 同一群中，经过身份核验且去重后的主人新发言将各成员 Bot 在该群的连续公开响应计数归零；重复平台事件、重试、其他群消息、Bot 发言或宿主重启都不能归零。计数和已确认响应身份持久保存；不同 Bot、不同群互不消耗额度。运行现场以 `publicReplyLimit` 提供权威 count／remaining／limit，模型可主动静默；发送端仍作最终限额检查，并以正常静默终态拒绝越限，不报告为平台故障或假称已投递。
- 内部定向咨询、交接及定时唤醒另保留同授权根的有限协调预算，现场字段为 `internalCoordinationBudget`，不再使用会混淆公开次数的 `automaticBudget`。该预算不限制普通群公共观察或收件，也不因公开计数归零而补满；内部消息不广播全群，平台 Bot 回流继续去重。已有执行助手正常交付保留现有保障，不能靠派生根、重试或定时新根绕过内部协调限制。
- 未送达、送达未知、已消费、静默和已接受任务分别记录。不得把“已登记”说成“对方已读／接受”，也不能把静默视为承担了执行责任。

### 临时分工与执行所有权

Bot 默认通用，模型或记忆的差异可形成不同判断；固定职责只能是用户选择的偏好，不是桥按平台分配的能力范围。交流与开工可以交错：一个 Bot 指出风险，另一个即可登记调查并验证，无需先开数轮会或达成全体共识。

主控直接使用已有的派工、续接和预约接口，不再先调用 `bridge_claim_work` 或事后调用 `bridge_finish_work`，也不需要自行编造任务编号。桥在实际派工入口自动登记任务身份、目标、负责 Bot、原授权、交付地址和声明资源，将实际助手关联到该登记；已确认的派发重试复用原登记，不新建第二个助手。继续同一助手沿用可核实的归属，不能借续接接管其他 Bot 的助手。独立子任务可并行；同工程写入或浏览器资源仍按声明的实际冲突检查。

助手排队、执行、结束和结果未知由程序事实维护。正常结束或已确认停止后才收口相应执行登记及释放资源；失败、取消、原生会话交还、远端断线和桥恢复均保留真实状态，结果未知或停止未确认不能伪装成已完成。预约尚未触发不算正在执行；已经启动的助手不因其他 Bot 更新现场而被取消。一轮助手结束只表示执行结束，不代表用户目标已达成，主控仍负责核对结果和必要的后续工作。

桥只保证登记的负责人、已声明资源互斥与派发幂等，不按谁先激活或自然语言相似度判断任务重复。不同描述的同一问题仍可能被分别调查；模型结合最新现场决定是否补充或独立验证，不能承诺零重复。多 Bot 的效果须用重复调查率、模型调用成本和交付耗时验证，不能把发言数量当成提效。

### 主控可见现场与慢响应刷新

现场版本是程序维护的可见事实位置，不是认领次数、模型能力评分或新的主控工具。每轮保存实际交给此主控的现场位置；桥收集当前授权工作群的新公开发言、非负责人的只读现场，以及本群程序确认的助手派发／结束事实。Miku 尚未公开说话但已经派出助手，也应形成可查询的简短进展。群任务的短标题属于共享群现场，不应包含未经授权披露的私聊资料或无关隐私；详细执行指令和内部任务正文不因此公开。普通聊天、执行进展和授权性质分开记录，不把程序事实伪装成真人新指令。

- 只比较该主控有权看到、且比当前原生决策起点更新的事实。自己的同步发送和派工事实视为本人已知；重复平台回流、重复派发回执、服务状态提示不制造新变化。检查点在真正开启原生决策时确认；主动调用 `bridge_group_context` 查询最新现场不直接推进检查点，避免同一旧响应并行查询和派工时借查询放行旧动作。由此可能发生一次保守的冗余刷新，仍受原请求的持久次数上限约束。其他群、他人私聊和内部任务正文不能借刷新混入本群现场。后台通信保持 `internalBotCommunicationEnabled: false` 时不新增内部定向消息；内部内容不能改投公开群。
- 不在请求仍由网关处理时假称已更新模型输入。慢模型返回、准备派助手或公开发送前，桥检查此轮输入后是否出现新的可见事实；需要刷新时先不执行旧响应中尚未执行的副作用调用，将有界、去重的最新增量补给同一主控，由模型重新判断继续、换方向或静默。不能先启动一个助手、再把同一旧响应中的另一个派发拦下而声称整批未执行。
- 每个原始主人请求对每个 Bot 最多额外刷新一次；同一请求派生的协作根、公开观察和助手结果共用这一份持久预算，宿主重启不补满。同一旧响应的多个工具调用共享暂停决定，不能让第二个并发调用绕过，也不能把每个工具调用或后续观察当作新的重判机会。刷新后再来的现场更新正常入队，不不断追加模型回合。此边界控制开销，意味着仍存在刷新后又发生新变化的窗口，不能宣称绝不基于稍旧现场行动。
- 刷新不给旁观成员、Bot 发言或引用新增执行授权，不把不同主人请求合并成一个授权根，也不更改原交付区域。每次真实派发与发送仍独立复核主人、成员、群绑定、主控代次、任务归属和资源约束；刷新额度用完不能绕过这些硬检查。
- 静默不回复继续是群聊的正常终态，私聊真人输入仍需回复。现场变化不自动取消已执行动作、不回滚已送达消息、不打断已经运行的助手，也不按关键词决定谁该回答。补送事实供模型判断，不添加角色、人格或低能力模型专用规则。

### 任务交接

咨询与转交责任分开。咨询不改变负责人；本节交接流程依赖内部定向通知，仅在 `internalBotCommunicationEnabled: true` 时开放；关闭时拒绝新提议与接受，并取消仍处于 `proposed` 的旧提议；不取消任务、不转移原负责人与资源，不自动改成群公开交接，再次开启不会复活已取消提议。交接使用持久的 proposed → accepted / rejected / cancelled 状态：

1. A 传递已授权任务的目标、当前证据、交付判据、资源约束及原回复地址，不复制全部会话。
2. A 若仍有为该任务产生副作用的执行助手或后台进程，先完成或确认停止原执行；未确认时保持等待／待核对，B 不得开工。B 接受后再以原子操作转移 taskId 的执行所有权；同一任务任一时刻只有一个负责 Bot。修改负责人记录不能替代确认原进程已停止。
3. 目标离线或未接受时，A 仍负责，不得称“已交接完成”。接收任务使用 B 自己的模型与执行助手默认策略。
4. 群负责人 `/stop`、相关 Bot `/new`、成员撤销或权限撤销会关闭尚未接受的交接。旧结果不能唤醒新会话代次。
5. 协作可调度现有执行助手，但不能伪装接管另一个主控名下的助手。需要移交助手时遵循独立的可验证接管协议。
6. 多 Bot 共享电脑、工程和浏览器时，按 taskId 维持负责人。已声明的同一工程写入／浏览器资源冲突由宿主拒绝并回报当前负责人，主控据此等候释放、咨询负责人或拆分独立任务；无法识别的资源由相关主控在工作区层协商隔离，不把协调规则塞给每个执行 Agent 的全局上下文。

## 8. 批量 /new、并发和失败处理

群 `/new` 不是向 N 个 Bot 各自模拟一条用户消息，而是一个宿主操作。一个请求具有固定的 operationId、操作者、成员快照、影响入口列表及每 Bot 执行状态。

1. **预检。** 原子认领或验证负责人，核对所有明确成员的身份、主人、在群状态、连接和初始化条件。已登记成员离线、归属冲突或权限未知则拒绝；不能只重置一部分后声称全部完成。
2. **冻结。** 宿主将控制操作持久入队，按固定 botId 顺序取得目标控制锁；暂停这些 Bot 的新轮次，建立清晰输入边界。跨群的重叠重置串行，避免双向等待。
3. **结束旧预约。** 取消所有目标旧主控的定时，停止它们已经启动的定时助手，并确认结束。任何一项未确认则不切换主控。已发生的取消不可谎称回滚，回执列出部分取消及阻塞项。
4. **准备与提交。** 准备新会话记录后，在宿主的权威当前会话表里一次提交全部 conversationId / generation，随后恢复目标 Bot 队列。跨 Bot 数据文件不能各自保留互相矛盾的 active 指针。
5. **初始化。** 提交后并行执行各 Bot 的默认初始化助手。个别初始化失败标记为失败／未就绪，不假称整个批次已经就绪，不偷偷恢复旧上下文。
6. **回执。** 收件 Bot 发一份黄色批量操作回执，列出成功、初始化中和失败项，并说明影响私聊及其他关联群。不让每个 Bot 自动刷一份介绍；私聊 `/new` 保留现有初始化介绍体验。

边界处理：

- 同一 Bot 私聊与多个群同时输入时，按宿主持久接收顺序进入同一队列；不分别打开两个相同 nativeId 的活动轮次。
- 控制命令沿用现有优先处理方式；重置前已排队的旧输入取消，重置后收到的输入等待新代次，不穿越边界。
- 相关旧协作请求停止唤醒；旧定时结果只留存。普通工程助手遵守原 `/new` 规则：可完成但不自动接管；旧结果不进入新会话，若通知则标明旧会话并只发原入口。
- 初始化任务和助手默认模型来自各自 Bot 的配置／选择，不让远端机器的任意 CLI 默认决定模型。
- 断电若发生在取消与提交之间，按操作日志恢复“待核对”；不重放模型生成，不伪造原子回滚。
- Bot 变更模型、强度、当前会话、主人或群绑定的控制写入串行；不同 Bot 的普通推理与独立执行任务不互相等待。

## 9. 去重、权限变化与恢复

- 宿主控制库保存 principal 映射、群绑定、每 Bot 当前会话指针、操作日志、群记录、收件去重和协作 outbox；Bot 数据分区保存其会话、助手、计划、上下文和原生资料。目录使用真实 botId 派生的安全稳定键，不能直接把含冒号的身份串用作 Windows 目录名，也不随 Profile 改名换目录。
- 同一平台消息经多个连接收到时，由收件 Bot 提供普通人类消息的权威观察，其他连接不直接派工；宿主先去重一次，再生成各目标的参与事件。一个平台输入可以合法触发多个成员参与，但只有一个根请求；原生命令仍只执行一个控制操作，interaction 按其真实 ID 去重。
- 未激活群的首次管理指令要求明确点名一个 Bot／选择一个应用；宿主对群认领事务唯一约束，即使同时收到也只成功一次。
- Canonical space / principal 映射必须经平台事实或显式本地映射证明；不能用消息文字、近似时间、显示名相同来猜测同一个事件、用户或群。
- 收件 Bot 无法读取普通群消息时，群不得宣称完整可用；明确点名控制指令仍可用于重新选择满足条件的收件入口，不改变其他主控身份。
- 内部消息按 (逻辑事件, 目标 Bot, generation) 去重；发送状态包含 registered、delivered、uncertain、rejected。不承诺平台网络下的严格 exactly-once，不盲目重发未知结果。
- 每次执行与投递前复核负责人、bindingEpoch 及当前成员权限；revision 改变时重验相关成员，不把单纯换收件 Bot 当成所有旧任务失效。在队列里排过队不等于永久拥有发送权限。
- 宿主重启恢复 owner、成员、收件 Bot、原生 ID、指针、队列、计划、参与游标、每 Bot／每群公开计数、内部根预算及静默终态，不重新认领群、不自动初始化所有 Bot，也不重放已完成的静默判断。
- 宿主仍通过监督器排空当前轮次与回执后重启；未来定时计划保留。Bot 私聊的 `/restart` 是宿主级操作，涉及该宿主全部 Bot，不能只等发起者空闲。
- 生命周期沿用平台既有私聊通知／状态栏表达；不因为多个 Bot 或多个群而逐群重复广播。群输入不覆盖私聊生命周期通知的最后联系人。
- 某个 Bot 的认证、连接或模型失败单独标记，其他 Bot 继续运行；批量命令仍必须如实列出不可执行项。

- 至少收件 Bot 需要普通群消息与历史所需权限；仅有群 @消息权限不足以承诺无 @输入也能工作。其他成员可由桥接收公共事件，但仍需确认在群、能发消息及身份映射有效。[官方权限示例](https://open.feishu.cn/solutions/detail/ticket?lang=zh-CN)、[群历史前提](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list)
- 文本命令及原生提及由适配器解析；不假称已有 Discord 式原生斜杠菜单。
- 不默认跨应用的 chat_id、message_id 和资源 key 可以互换。群别名映射、同消息多应用观察、成员进退事件须用真实应用验证。
- 飞书实体提及按观察应用的 ID 空间解析；其他 Bot 的 open_id 不直接当作当前应用身份。跨应用点名通过各自凭据只读核对同条消息、显式群映射、时间、负责人、内容和提及 token；仅由收件 Bot 派发。真人提及先核对群成员，无法证明的实体标为未知，不猜成全员提及；身份核对不改变普通主人群消息的全体就绪主控收件范围。核对保持接收顺序，恢复及异步核对后重验绑定和代次。

### Discord

- 以频道或已有话题为 Space，guildId 仅作为上层元数据；不把整个服务器认作一个工作群。
- 原生指令属于收到 interaction 的应用。桥将其翻译为群操作，再按群成员快照分发，不能等待其他应用收到同一条 interaction。[官方 Application Commands](https://docs.discord.com/developers/interactions/application-commands)
- 注册表要区分 GUILD 与 BOT_DM 场所；群只展示子集，桥仍做负责人校验。原生权限和菜单显示不能替代内部校验。
- 普通频道输入和历史读取需实际所需的 Gateway intents、频道权限及 Message Content 能力；不具备时明确受限，不空读后声称已经理解全群。[官方 Gateway](https://docs.discord.com/developers/events/gateway#message-content-intent)
- 提及只使用已解析、被允许的真实 Bot ID；普通生成文本不得任意触发 @everyone 或无关成员。

共同门槛：跨 Bot 的操作者／群标识映射、收件能力和两个真实 Bot 的定向对话均需在开发前做最小探针。官方说明是设计依据，不代表当前部署已经开通这些权限。

## 12. 开发顺序、Git 边界与发布

1. **平台探针与数据设计。** 验证第 10 节门槛；冻结身份映射、群地址规范化与权限配置，准备迁移清单。探针结果仅存本地证据，不提交密钥和真实聊天记录。
2. **多 Bot 宿主与单操作者主控。** 完成 BotRuntime 隔离、启动集合、owner 认领、宿主级重启及恢复；先验证两个 Bot 私聊互不串线。
3. **Space 与公共群命令。** 增加群绑定、收件入口、固定默认回复来源及共享主控队列；完成 group start/stop/status/new/stop 与多群边界。
4. **自主参与与协作。** 加入运行时现场、全体首次参与、合并观察、静默结束、去重 outbox、受众明确的发送工具、派工自动登记、可选交接所有权和有限预算；慢响应按可见事实为每个原始主人请求、每个 Bot 最多额外刷新一次，派生根共享且重启不补满，群任务与普通执行助手分层展示。
5. **真机验收。** 从两个通用 Bot 开始，覆盖 A01–A37；用同类任务对照单主控，记录首次有用回复时间、交付耗时、模型调用／静默成本、重复工作和用户纠正次数，再扩展成员规模。飞书和 Discord 分别验证同样行为及本机菜单，不能把某平台未完成的验收写成能力已对齐。

迁移要求：

- 停止旧宿主后备份，生成可审查的一次性迁移清单；单一 startupProfile 转成只有一个元素的启动集合，私聊使用体验保留。
- 按已验证的真实 Bot 身份拆分会话、助手、计划和原生资料归属；每个 Bot 的数据目录独立，公共群与控制数据归宿主。
- 如果旧数据中同一 Bot 存在多个用户的活动会话，必须明确选择保留哪一个作为当前主控；其余保留历史，不按“最近一条”自动抢占。
- 原会话 ID、nativeId、模型选择、任务结果及计划引用保留；重定位资料时更新并验证路径。不能通过重新生成摘要冒充续接原会话。
- 本轮群绑定此前不存在，迁移后全部未激活；不得把旧私聊联系人自动当作群负责人。
- 移除按用户分配多个当前主控的旧索引和入口，更新全部队列及权限调用，不保留暗中的旧语义分支。
- 主控管理工具声明变化后，为各 Bot 分后端核对初始化／续接：当前 Codex 旧会话的动态工具表不会因普通宿主重启自动刷新；Claude 冷启动会重新提供 MCP 工具与提示并续接原生 ID，须用新工具实际调用证明已刷新。是否用私聊 `/new continue` 提炼旧上下文应作为发布操作明确记录。
- 恢复旧版本只能通过一致的备份恢复，不用兼容代码在新旧所有权语义间混跑。

Git 管理：提交领域规则、配置 schema／脱敏示例、迁移工具、命令注册表、测试和本文。真实 Bot 凭据、Principal 映射、群绑定、个人三文件上下文、会话数据库、附件及探针结果留在 `.local` 或用户自己的上下文目录，不进 Git。

后续开发可直接引用本文与 A01–A31。产品主线已有决策，剩余的平台实测门槛明确列在第 10 节；其结果不满足时，应先报告能力缺项并修订设计，不能静默换成另一套群行为。

## 13. 本轮实施与验收边界（2026-10-17）

已实施的程序职责：

- `HostRuntime` 维护启动集合、Bot 主人及当前主控权威指针、真实 Principal / Space 映射、负责人权限、群命令和逐事件固定回复地址。`BotRuntime` 各自持有平台连接、主控、执行助手、私聊收件和上下文；一个项目仍只有一个监督进程和重启生命周期。
- `HostStore` / `HostInbox` 持久保存代次、群绑定、全体首次参与、队列、公共记录与游标、每 Bot／每群公开计数、内部协调预算、静默终态、受众 outbox、任务与资源声明、交接、批量重置日志。不同 Bot 的附件准备和推理独立；相同 Bot 的主控活动串行。
- 主控工具提供群现场、内部定向咨询、授权投递区域查询、补充发送、最终发送选目标、执行任务认领与交接、静默结束。本人私聊与已激活工作群可从私聊或群轮次明确选为投递区域；默认交付沿用原输入，选择其他区域不更改任务的归属和交付目的地。每次发送重验来源、当前会话、负责人、群绑定及目标权限，未知发送不重试。声明资源冲突会拒绝，助手须据现场等待或拆分独立任务，程序没有擅自重派队列。
- `/agent` 真切换从当前 Bot 最新主控交接到新后端原生会话，成功后提交并重绑助手和计划；摘要使用独立只读执行环境。选择同后端不切换。失败和提交日志中断按事实恢复，不返回旧后端分支。`/new continue` 只读当前 Bot 的源上下文，仍遵循新会话取消旧预约的规则。
- 批量 `/new` 一次提交全部当前主控指针，再分别初始化。提交前中断保留待核对和已发生的取消；提交后只恢复尚未完成的初始化。真实载入状态先持久化，再通知宿主；未知状态不自动重跑。
- 重启时，未开始的预约和队列保留；已开始的模型轮次不重放。只有进程停止的程序证据才能释放不确定的原生活动槽。发送结果未知的 outbox 不盲重发；群停用或权限撤销后保留任务结果，不改投最近入口。
