# 群聊与多个长期主控 Bot：扩展设计

状态：设计基线 v1，尚未实施。日期：2026-10-16。代码核对基线：`02db109`。
本文件是后续开发入口；README 中的现有使用方式仍然有效。本次只提交设计，不修改运行中的桥、主控提示词或个人记忆。

## 1. 产品目标与决策来源

目标是多个独立 Bot 在同一聊天平台同时运行，在群中讨论、交接、分别派执行助手；Bot 的身份、当前上下文和职责能够从私聊延续到群中。

用户已明确的规则：

- Bot 的身份与启动独立于聊天用户；同一平台可以同时启动多个 Bot。
- 私聊准备过的 Bot 进入工作群后应能继续；没有主控会话的 Bot 仅被拉进群不会启动主控。
- 同一 Bot 的私聊与工作群共用主控上下文。用户已明确接受：群 `/new` 重置相关 Bot 时，也重置它们私聊正在使用的上下文，取消旧定时并停止已启动的定时助手。
- 群 `/new` 可以初始化或重置本群的全部桥 Bot，而不只是收到该命令的一个 Bot。
- 群由首个满足白名单条件并成功激活的用户控制，普通群员及其他白名单群员的输入不触发工作。
- Bot 之间能接收协作消息；群的命令清单应比私聊少。
- 不做旧语义兼容层；改动现有数据语义时，应有完整、可检查的一次性迁移。

本轮选择的首版方案（不是声称用户逐项确认了接口拼写）：

- **一个 Bot、一个当前主控、一个激活用户。** 多个白名单用户可分别使用不同 Bot，同一个 Bot 不并行维护多名用户的当前主控。
- **支持同一 Bot 参与多个工作群。** 用户将首版范围的权衡交给实现者；采用共享上下文、逐事件固定回复地址的方式，不为每个群复制主控。
- 群激活与新建会话分开，暂定 `/group start` 与 `/new`。普通群消息先交给默认协调 Bot，明确点名则交给指定 Bot。
- 保持现有重任务委派方式。主控是否增加直接查询、记忆读写或 Bash 权限，是独立议题，不作为本功能的前提。

## 2. 首版范围与当前缺口

支持：同平台多 Bot、私聊与多个工作群续用主控、单操作者权限、群命令、定向协作与任务交接、重启恢复。飞书与 Discord 共用领域规则和命令语义，适配器处理身份、收件、菜单、提及和排版。

不纳入：同一 Bot 的多用户独立会话、在线转移主人、跨平台同一主控、陌生 Bot 联邦、自由抢话、群语音、自动跨群转发、严格的同一 Bot 跨入口信息隔离、为本功能直接开放主控 Bash。

| 当前代码事实 | 开发时必须改变的地方 |
| --- | --- |
| `src/main.ts`、`src/instance-lock.ts`：同一项目只运行一个所选 Profile | 一个宿主管理同平台多个 BotRuntime；继续防止同一真实 Bot 重复登录 |
| `src/manager.ts`、`src/store.ts`：当前会话、运行队列等大量按 userId 索引 | 身份与当前主控按 botId 索引；userId 只参与认证及操作者映射 |
| `src/feishu.ts`：仅接收白名单用户 p2p；`src/discord.ts`：排除 guild 和 bot 作者 | 接入群入口，保留对未授权人和未知 Bot 的过滤；内部协作独立于外部 Bot 消息 |
| `src/slash.ts`：仅 BOT_DM；`src/commands.ts`：一份共用命令表 | 命令增加允许的场所、目标范围及所有者要求，避免两个平台维护两套行为 |
| `src/controller/native.ts`：只有桥管理工具；`src/controller/runtime.ts`：助手归原主控 | 增加长期 Bot 协作能力声明，保持执行助手与长期主控两个层级 |
| `src/ingress.ts`、`src/restart.ts`、`src/lifecycle.ts`：已有持久收件、排空和恢复 | 扩展为宿主级控制与 Bot 级队列，不能在重启时重新认领用户或初始化 Bot |

## 3. 领域对象与不可变规则

| 对象 | 稳定身份与职责 |
| --- | --- |
| Bot | `botId = platform + verifiedApplicationId`。Profile 别名、显示名或密钥变化不改变身份 |
| Principal | 桥内操作者身份，映射各应用下的真实平台用户 ID；不是显示名 |
| Controller | 一个 Bot 的当前原生主控会话；保存 conversationId、nativeId、generation、模型与强度 |
| Space | 一个飞书群或 Discord 频道／话题；Discord 服务器只是上层容器 |
| GroupBinding | Space 的负责人、协调 Bot、明确的成员 Bot 集合、绑定 epoch、成员 revision 及启用状态 |
| Event | 原始来源、操作者、目标 Bot、原会话代次、固定回复地址、可见范围、因果链及幂等 ID |
| Work / Handoff | 任务身份、当前负责 Bot、授权来源、交接状态和结果；执行助手仍归具体主控会话 |

约束：

1. Bot 的 ownerPrincipalId 在首次有效初始化时确定；`/new` 不释放或改变主人。可预配置主人，首次输入必须匹配。
2. 激活用户是当前主控的控制者，不是 Bot 身份的组成部分；改用户名、群名或 Profile 名不影响既有会话。
3. 一个工作群只有一个负责人；成员 Bot 必须属于该负责人，或尚未初始化且可由其合法激活。其他人拥有的 Bot 不纳入本群。
4. 一个 Bot 可以关联多个群，但同一原生主控一次只运行一轮；不同 Bot 可以并行。
5. 所有私聊、群、助手结果、协作和定时事件进入同一个 Bot 队列。不能继续按“一个用户一条队列”串行所有 Bot。
6. 一轮的回复地址在收件时确定。后来的私聊、另一个群的消息或“最后联系用户”不能覆盖它。
7. 同一 Bot 在所有入口共用当前 generation。群 G1 重置 Bot A，A 在私聊和 G2 也会续用新会话；没有涉及的 Bot 不重置。
8. 共享上下文不代表程序会复制私聊记录到群，但也不提供严格的信息隔离。需要隔离记忆或保密边界的工作，应使用不同 Bot。
9. 首版主人不在线转移。其他白名单用户不能通过私聊 `/new`、群激活、修改显示名或移除群成员来抢占。
10. 白名单撤销后立即拒绝该人的新输入，并暂停其群入口；不自动把已有上下文交给下一名白名单用户。新 Bot 的身份、权限映射及启动成员仍在启动前配置。

## 4. 身份、启动和上下文

宿主按启动配置加载一组同平台 Profile。一个 Profile 对应一个真实 Bot。连接平台、拥有主控、参加工作群是三个独立状态：

- 平台连接就绪不自动新建主控；没有会话的 Bot 只接收必要的管理和初始化指令。
- 私聊保留现有体验：`/new`，或首次合法普通输入产生的自动新建，均建立该 Bot 的主控并绑定操作者。
- 私聊里设置的模型、强度、职责和当前上下文，随同一 Bot 进入群；不会因群激活而改成协调 Bot 的模型。
- 目标语义中，Agent／模型／强度选择属于 Bot 的持久设置；`/new` 重建工作会话并沿用这些选择，只有显式设置 `default` 才恢复相应默认。实际模型回报仍单独记录。若现有私聊实现与此不同，应在本次语义迁移中明确调整并验收，不能以群激活为名偷偷改值。
- 各 Bot 使用独立的上下文工作区，沿用 `README.md / AGENTS.md / MEMORY.md` 三文件约定；共用知识由明确链接引入，不复制其他 Bot 的全部记忆。
- Bot 的上下文工作区与执行任务的 workingCwd 分开；私聊 `/cwd` 调整工作目录时，不能把身份、主人或 MEMORY 写到另一个 Bot 的目录。
- 各执行 Agent 继续使用所在电脑已有的 CLI、网关、技能及认证。用户自定义模型别名不需要因官方模型名不一致而受质疑。
- 启动集合、身份映射、凭据和网络预设不通过群聊修改。每个 Bot 的代理设置独立，不能把 Discord 的代理隐式套给飞书。
- 下线某个 Profile 不等于注销它的身份或删除会话；其他 Bot 不应受影响。

目标配置可采用 `startupProfiles` 数组（单 Bot 也是一个元素），而不是为了多 Bot 同时运行多个竞争同一项目锁的旧启动脚本。字段名称可在实施时细化，语义必须一致。

## 5. 群激活、成员和退出

### 首次激活

未激活的群不把普通消息送给模型。用户需通过明确点名某个桥 Bot 的文本指令，或选择该应用的原生指令入口，提交 `/group start` 或 `/new`，避免多个 Bot 同时抢答。

`/group start`：

1. 验证调用者为有效白名单用户、确实在群中，并满足所有目标 Bot 的身份映射与控制权要求。
2. 冻结本次明确、可核实的候选成员集合，持久登记负责人；并发认领由宿主事务裁决，先成功者生效。
3. 以被点名／被选择应用的已初始化 Bot 为默认协调者。它必须能读取本群所需消息；不满足则拒绝并说明缺项，不随机选另一个。
4. 接续候选中已经属于该操作者的主控。未初始化者标为“未初始化”，不为其调用模型。
5. 发一次简短回执，列出负责人、协调者、参与 Bot 与未就绪项。声明“激活成功”必须与实际持久状态一致。

`/new` 可在未激活群中完成认领并批量初始化，详见第 8 节；此时不要求协调 Bot 预先有主控。

### 成员变化

- 群成员集合不是“群里所有机器人”：只包含本宿主登记、确认在群中、符合当前负责人权限的桥 Bot。
- 显示名或模型文本中的“@某 Bot”不能证明真实身份；使用平台的提及实体和配置中的真实 Bot 身份。
- 新 Bot 入群不自动加入工作集合。负责人再次 `/group start` 刷新成员并接续已初始化者；群 `/new` 则初始化／重置刷新后的集合。
- 不能把未知在群状态当作已加入；回执报告未纳入项。已登记成员暂时离线不能在批量操作中被静默跳过。
- “全部”始终指本群明确登记的成员快照；不属于当前操作者的 Bot 要在回执中列为未纳入，不得借群命令接管。
- 未登记的外部机器人、Webhook 和普通群员都不成为协作主体。
- 协调者离线时不自动切成另一种模型。负责人可点名一个就绪成员执行 `/group start`，显式更换协调者。
- 完全相同的 start 不改变版本；成员／协调者更新只增加 revision，并复核相关权限，不取消无关的原任务。停用后重新激活才产生新 epoch，旧 epoch 不自动恢复投递。
- 群负责人退出／失去访问权时暂停整个绑定，不自动让第二个白名单用户继承；Bot 私聊和其他群仍可继续。

### 停用群

`/group stop` 停止本群的新输入、协作唤醒及公开投递，保留 Bot 的主控和长期记忆。它不等于 `/stop`：

- 已获授权的执行任务与计划保留；结果存回原任务记录，不在停用群中发送，也不自动改投另一个群或私聊。
- 正在发送的请求只能记录实际送达状态，不能承诺撤回已发生的投递；停用后不再发新的普通回复。
- 已排队但未启动的本群普通输入与协作事件取消；其他入口的队列不受影响。
- 已启动的协作工作继续归当前负责 Bot；向停用群的回送标记为“目的地不可用”，不得无限重试。
- 需要停止工作的用户应先使用 `/stop`。重复停用幂等；重新激活产生新绑定版本，不自动重放停用期间的消息。
- Bot 被移出某群时只撤销它在该群的绑定；它在其他群的工作不会被顺带停掉。

## 6. 群命令与普通消息路由

命令仍来自同一份注册表；增加场所、目标和权限元数据，由平台渲染菜单。下表是首版目标语义，名称尚未发布。

| 命令／输入 | 范围与行为 |
| --- | --- |
| `/group start` | 认领或刷新当前工作群，接续已有主控，选择接收指令的 Bot 为协调者；重复调用不重置上下文 |
| `/group stop` | 停用当前群绑定，不重置主控、不停止其他入口 |
| `/status` | 汇总本群成员、负责人、协调者、初始化及连接状态，不创建主控 |
| `/workers [history] [details]` | 汇总本群任务来源的助手，标出所属 Bot；历史按末轮结束时间倒序；不泄露其他群或私聊任务正文 |
| `/new` | 初始化／重置本群全部明确成员；影响这些 Bot 的所有入口，并取消旧定时 |
| `/stop` | 停止本群成员 Bot 当前受桥管理的主控／助手工作和预约，清空其共享会话队列；会影响私聊和其他群，回执必须说明 |
| `/help` | 仅列当前场所允许的命令，并解释群命令范围 |
| 负责人 `@Bot B` 的普通消息 | 定向提交给 B；对未初始化 B 仅回控制提示，不自动创建主控 |
| 负责人未点名的普通消息 | 只唤醒本群协调 Bot；它可按任务需要找其他成员 |
| 其他人／未知 Bot 的消息 | 不触发模型、下载附件、派工或记忆写入 |

补充规则：

- 群 `/new` 和 `/stop` 是全体命令；Discord 菜单选择哪个应用只决定收件入口，不把范围缩成该应用。
- 首版不提供群 `/new continue`、模型／强度切换、目录切换、Agent 切换和宿主重启；在目标 Bot 私聊中操作。参数不支持时明确报用法，不忽略参数后执行。
- 私聊 `/workers` 仍可查看该 Bot 的受管助手；群列表按 originatingSpaceId 过滤。交接后的任务仍可由原群查到完整负责人链。
- 私聊 `/new` 只重置目标 Bot，但因为上下文共享，它所在的各群也续用新会话。
- 同时点名多个 Bot 时视为一个根请求，由协调者保存目标集合并安排；不能把同一任务复制成无关联的多份。
- 原生菜单不可见不能替代桥自身的权限检查。负责人之外的人即使绕过菜单发文本指令，也不会执行。

## 7. 群记录、回复地址和 Bot 互通

### 共享记录与固定来源

宿主持久保存已授权的群输入及桥 Bot 的群发言。成员 Bot 的下次定向唤醒可以读取有界的公共记录，保留每个 Bot 的独立私聊、职责和长期记忆。

事件至少携带：eventId、rootRequestId、causeEventId、principalId、sourceBotId、targetBotId、spaceId、bindingEpoch、membershipRevision、conversationId、generation、replyTarget、授权任务引用及附件引用。

- 私聊回复回原私聊，G1 回复回 G1；不使用“最后收到消息的群”作为回复目标。
- 助手结果、定时计划和后续追问继承原任务来源；交接任务也保留原交付目的地。不能因为执行 Bot 最近在 G2 聊天，就把 G1 的结果送去 G2。
- 定时自唤醒不创造新的用户授权；工作群停用／失权时按“结果留存”规则处理，不自动换目的地。
- 普通群员及其他白名单用户的发言不自动作为旁听上下文；负责人明确引用的内容可作为资料，不能当成新的授权。
- 共用原生上下文会让同一 Bot 知道多个入口的信息；程序保证来源与投递绑定，不承诺模型层面的严格保密隔离。
- 不自动把整份私聊记录、个人 MEMORY 或助手完整日志贴到群里；显式附件仍需实际授权、文件范围及大小检查。
- Bot A 下载的附件通过带来源和权限的桥内引用分享给 B；B 发图／文件时使用自己的平台凭据重新上传，不复用另一应用的资源 key。

### 接收不等于唤醒所有模型

所有有效公共发言都可进入群公共记录；只有负责人输入、明确点名、对已登记请求的回答、任务交接或结果事件才唤醒相应 Bot。

- 互通由桥内部的持久事件保证，不依赖平台把 Bot 消息发给另一个 Bot。
- 首版互通必须关联一个双方都参加、负责人一致且仍启用的工作群；私聊发起群协作时必须明确目的群，不能默认选最近活跃群。其他群的 Bot 不因名字相同而成为目标。
- 不把 Bot 发言伪造成用户消息，不允许其直接执行 `/new`、`/stop`、认领群或修改白名单。
- 原始群发言进入共享记录时不自动唤醒全体。A 点名询问 B，B 回答可按 requestId 唤醒 A 一次；未被点名的 C 不需跟着生成回复。
- 群公开消息由实际发言 Bot 发出。桥管理工具仍默认静默；普通发言遵循“管理操作完成后公开发布、随后结束”的现有协议。
- 公开发言携带的提及和内部定向事件应属于同一逻辑消息；平台回流只补齐送达证据，不能再次触发同一接收方。
- 每个根请求默认最多触发 8 次跨 Bot 模型唤醒，回复也计入；预算耗尽时停止自动互唤并反馈一次，不能靠定时重开根请求绕过。数值可配置，必须有限。
- 未送达、送达未知和目标离线要明确区分。不得把“已登记”说成“对方已读／接受”。

### 任务交接

咨询与转交责任分开。咨询不改变负责人；交接使用持久的 proposed → accepted / rejected / cancelled 状态：

1. A 传递已授权任务的目标、当前证据、交付判据、资源约束及原回复地址，不复制全部会话。
2. A 若仍有为该任务产生副作用的执行助手或后台进程，先完成或确认停止原执行；未确认时保持等待／待核对，B 不得开工。B 接受后再以原子操作转移 taskId 的执行所有权；同一任务任一时刻只有一个负责 Bot。修改负责人记录不能替代确认原进程已停止。
3. 目标离线或未接受时，A 仍负责，不得称“已交接完成”。接收任务使用 B 自己的模型与执行助手默认策略。
4. 群负责人 `/stop`、相关 Bot `/new`、成员撤销或权限撤销会关闭尚未接受的交接。旧结果不能唤醒新会话代次。
5. 协作可调度现有执行助手，但不能伪装接管另一个主控名下的助手。需要移交助手时遵循独立的可验证接管协议。
6. 多 Bot 共享电脑、工程和浏览器时，按 taskId 维持负责人。已声明的同一工程写入／浏览器资源冲突应由宿主排队；无法识别的资源由协调主控在工作区层安排隔离，不把协调规则塞给每个执行 Agent 的全局上下文。

## 8. 批量 /new、并发和失败处理

群 `/new` 不是向 N 个 Bot 各自模拟一条用户消息，而是一个宿主操作。一个请求具有固定的 operationId、操作者、成员快照、影响入口列表及每 Bot 执行状态。

1. **预检。** 原子认领或验证负责人，核对所有明确成员的身份、主人、在群状态、连接和初始化条件。已登记成员离线、归属冲突或权限未知则拒绝；不能只重置一部分后声称全部完成。
2. **冻结。** 宿主将控制操作持久入队，按固定 botId 顺序取得目标控制锁；暂停这些 Bot 的新轮次，建立清晰输入边界。跨群的重叠重置串行，避免双向等待。
3. **结束旧预约。** 取消所有目标旧主控的定时，停止它们已经启动的定时助手，并确认结束。任何一项未确认则不切换主控。已发生的取消不可谎称回滚，回执列出部分取消及阻塞项。
4. **准备与提交。** 准备新会话记录后，在宿主的权威当前会话表里一次提交全部 conversationId / generation，随后恢复目标 Bot 队列。跨 Bot 数据文件不能各自保留互相矛盾的 active 指针。
5. **初始化。** 提交后并行执行各 Bot 的默认初始化助手。个别初始化失败标记为失败／未就绪，不假称整个批次已经就绪，不偷偷恢复旧上下文。
6. **回执。** 协调 Bot 发一份黄色批量操作回执，列出成功、初始化中和失败项，并说明影响私聊及其他关联群。不让每个 Bot 自动刷一份介绍；私聊 `/new` 保留现有初始化介绍体验。

边界处理：

- 同一 Bot 私聊与多个群同时输入时，按宿主持久接收顺序进入同一队列；不分别打开两个相同 nativeId 的活动轮次。
- 控制命令沿用现有优先处理方式；重置前已排队的旧输入取消，重置后收到的输入等待新代次，不穿越边界。
- 相关旧协作请求停止唤醒；旧定时结果只留存。普通工程助手遵守原 `/new` 规则：可完成但不自动接管；旧结果不进入新会话，若通知则标明旧会话并只发原入口。
- 初始化任务和助手默认模型来自各自 Bot 的配置／选择，不让远端机器的任意 CLI 默认决定模型。
- 断电若发生在取消与提交之间，按操作日志恢复“待核对”；不重放模型生成，不伪造原子回滚。
- Bot 变更模型、强度、当前会话、主人或群绑定的控制写入串行；不同 Bot 的普通推理与独立执行任务不互相等待。

## 9. 去重、权限变化与恢复

- 宿主控制库保存 principal 映射、群绑定、每 Bot 当前会话指针、操作日志、群记录、收件去重和协作 outbox；Bot 数据分区保存其会话、助手、计划、上下文和原生资料。目录使用真实 botId 派生的安全稳定键，不能直接把含冒号的身份串用作 Windows 目录名，也不随 Profile 改名换目录。
- 同一平台消息经多个连接收到时，不能触发 N 份命令。已激活群由协调 Bot 作为普通人类消息的指定收件入口；其他连接的重复观察不直接派工。原生 interaction 按其真实 interactionId 独立去重。
- 未激活群的首次管理指令要求明确点名一个 Bot／选择一个应用；宿主对群认领事务唯一约束，即使同时收到也只成功一次。
- Canonical space / principal 映射必须经平台事实或显式本地映射证明；不能用消息文字、近似时间、显示名相同来猜测同一个事件、用户或群。
- 协调 Bot 无法读取普通群消息时，群不得宣称完整可用；明确点名控制指令仍可用于重新选择一个满足条件的协调者。
- 内部消息按 (逻辑事件, 目标 Bot, generation) 去重；发送状态包含 registered、delivered、uncertain、rejected。不承诺平台网络下的严格 exactly-once，不盲目重发未知结果。
- 每次执行与投递前复核负责人、bindingEpoch 及当前成员权限；revision 改变时重验相关成员，不把单纯换协调者当成所有旧任务失效。在队列里排过队不等于永久拥有发送权限。
- 宿主重启恢复 owner、成员、协调者、原生 ID、指针、队列、计划及幂等状态，不重新认领群，不自动初始化所有 Bot。
- 宿主仍通过监督器排空当前轮次与回执后重启；未来定时计划保留。Bot 私聊的 `/restart` 是宿主级操作，涉及该宿主全部 Bot，不能只等发起者空闲。
- 生命周期沿用平台既有私聊通知／状态栏表达；不因为多个 Bot 或多个群而逐群重复广播。群输入不覆盖私聊生命周期通知的最后联系人。
- 某个 Bot 的认证、连接或模型失败单独标记，其他 Bot 继续运行；批量命令仍必须如实列出不可执行项。

## 10. 平台约束与验证门槛

### 飞书

- 使用应用机器人；Webhook 自定义机器人不能承担本设计的收件、主控与交互能力。[官方说明](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)
- 同一人的 open_id 在不同应用下不同。桥用 Principal 映射各 Bot 的应用内用户 ID；可使用已验证的同租户 user_id／合适作用域的 union_id 辅助映射，但不得默认跨租户或跨开发主体恒等。仅凭“黄永熙”等显示名不能关联。[身份说明](https://open.larksuite.com/document/home/user-identity-introduction)、[官方跨应用错误说明](https://open.feishu.cn/document/server-docs/api-call-guide/generic-error-code)
- 至少协调 Bot 需要普通群消息与历史所需权限；仅有群 @消息权限不足以承诺无 @输入也能工作。其他成员可由桥接收公共事件，但仍需确认在群、能发消息及身份映射有效。[官方权限示例](https://open.feishu.cn/solutions/detail/ticket?lang=zh-CN)、[群历史前提](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list)
- 文本命令及原生提及由适配器解析；不假称已有 Discord 式原生斜杠菜单。
- 不默认跨应用的 chat_id、message_id 和资源 key 可以互换。群别名映射、同消息多应用观察、成员进退事件须用真实应用验证。

### Discord

- 以频道或已有话题为 Space，guildId 仅作为上层元数据；不把整个服务器认作一个工作群。
- 原生指令属于收到 interaction 的应用。桥将其翻译为群操作，再按群成员快照分发，不能等待其他应用收到同一条 interaction。[官方 Application Commands](https://docs.discord.com/developers/interactions/application-commands)
- 注册表要区分 GUILD 与 BOT_DM 场所；群只展示子集，桥仍做负责人校验。原生权限和菜单显示不能替代内部校验。
- 普通频道输入和历史读取需实际所需的 Gateway intents、频道权限及 Message Content 能力；不具备时明确受限，不空读后声称已经理解全群。[官方 Gateway](https://docs.discord.com/developers/events/gateway#message-content-intent)
- 提及只使用已解析、被允许的真实 Bot ID；普通生成文本不得任意触发 @everyone 或无关成员。

共同门槛：跨 Bot 的操作者／群标识映射、收件能力和两个真实 Bot 的定向对话均需在开发前做最小探针。官方说明是设计依据，不代表当前部署已经开通这些权限。

## 11. 苏格拉底反例检查与验收编号

以下反例都必须有明确判定；括号中的 A 编号是开发验收项，不是本轮已执行的测试。

| 反问／反例 | 判定与验收 |
| --- | --- |
| A01：同一人在 A 私聊 new 后进 G1，会换成另一个主控吗？ | 不换；核对 botId、nativeId、模型、强度及可用上下文连续 |
| A02：没有会话的 B 被拉进群，会偷偷开模型吗？ | 不会；group start 报未初始化，group new 才创建它 |
| A03：两个白名单用户同时抢首次激活，或第二人私聊 new？ | 一个持久认领成功；另一个不能重置、调用模型或拿到私人正文 |
| A04：A、B 看到同一个人的不同 open_id？ | 经 Principal 映射识别；未证明映射则不授权；名字相同无效 |
| A05：同一 Bot 同时在私聊、G1、G2 收消息？ | 一个主控队列，回复分别固定回源，不以最后联系人覆盖 |
| A06：G1 new 重置 A、B，G2 只有 B、C？ | A、B 全入口切换；C 不动；G2 后续 B 使用新代次，旧事件不串入 |
| A07：group start 接续私聊、重复调用或更换协调者，是否误取消计划？ | 不取消、不新建、不换模型；相同调用不改版本，更换协调者不废弃无关任务 |
| A08：group new 的一个成员离线／停止定时进程未确认？ | 预检或切换前明确失败；不假称全成功；记录已发生的取消 |
| A09：群命令被多个 Bot 看见，或 Gateway 重发？ | 一个群控制操作、每个目标一次执行、一个汇总回执 |
| A10：A 公开提及 B，平台又把这条消息回流？ | B 只被定向唤醒一次；C 能读公共记录但不自动生成 |
| A11：Bot A 对 B 说“/new”，或群员冒充主人？ | 作为资料也不获得控制权；管理命令只接受真实授权的人类输入 |
| A12：A、B 互相问下去，或通过定时器绕过次数限制？ | 共享根请求预算有限；达到上限停止自动唤醒，不重开根请求逃逸 |
| A13：A 称交给 B，但 B 尚未接受／已掉线，或原执行进程尚未停止？ | 责任仍在 A，交接状态可查；B 不开工，不能产生两个执行负责人 |
| A14：B 接手后在 G2 发言，G1 的助手刚完成？ | 结果仍归原任务并投递 G1，不改投最近活跃群 |
| A15：停用群、负责人离群或 Bot 被踢，旧工作稍后完成？ | 按绑定范围停止投递，结果留存，不向别群泄露，也不自动换主人 |
| A16：取消一半时崩溃，或平台发送结果未知？ | 操作／outbox 状态持久可核对；不盲重跑模型，不声称回滚或成功 |
| A17：重启时有多个 Bot 和未来计划？ | 排空宿主活动，恢复原身份／绑定／计划，无重复初始化或群广播 |
| A18：跨 Bot 发图片文件，或不同 Bot 写同一工程／控制同一浏览器？ | 各用自身上传凭据；附件引用有来源；已声明冲突资源排队，不冒充全面自动防冲突 |
| A19：私聊模型切换、初始化失败、旧普通工程助手迟到？ | 群续用同一 Bot 新设置；失败可见；旧结果保留来源且不冒充新代次结果 |
| A20：多群并发 new 涉及同一 Bot，其他 Bot 在独立工作？ | 重叠控制写入串行；无关 Bot 推理不被串行全局锁堵住 |

“收到所有公共记录”“已加入工作群”“已接受交接”“已重启成功”分别需要自己的证据；不得用一次 API 注册成功替代后续全部阶段。

## 12. 开发顺序、Git 边界与发布

1. **平台探针与数据设计。** 验证第 10 节门槛；冻结身份映射、群地址规范化与权限配置，准备迁移清单。探针结果仅存本地证据，不提交密钥和真实聊天记录。
2. **多 Bot 宿主与单操作者主控。** 完成 BotRuntime 隔离、启动集合、owner 认领、宿主级重启及恢复；先验证两个 Bot 私聊互不串线。
3. **Space 与公共群命令。** 增加群绑定、协调入口、固定回复来源及共享主控队列；完成 group start/stop/status/new/stop 与多群边界。
4. **定向协作与交接。** 加入公共记录、去重 outbox、请求回送、交接所有权、预算及资源冲突约定；群任务与普通执行助手分层展示。
5. **真机验收。** 至少两个飞书应用 Bot，覆盖 A01–A20；再用 Discord 两个应用验证相同行为和本机菜单。不能把某平台未完成的验收写成能力已对齐。

迁移要求：

- 停止旧宿主后备份，生成可审查的一次性迁移清单；单一 startupProfile 转成只有一个元素的启动集合，私聊使用体验保留。
- 按已验证的真实 Bot 身份拆分会话、助手、计划和原生资料归属；每个 Bot 的数据目录独立，公共群与控制数据归宿主。
- 如果旧数据中同一 Bot 存在多个用户的活动会话，必须明确选择保留哪一个作为当前主控；其余保留历史，不按“最近一条”自动抢占。
- 原会话 ID、nativeId、模型选择、任务结果及计划引用保留；重定位资料时更新并验证路径。不能通过重新生成摘要冒充续接原会话。
- 本轮群绑定此前不存在，迁移后全部未激活；不得把旧私聊联系人自动当作群负责人。
- 移除按用户分配多个当前主控的旧索引和入口，更新全部队列及权限调用，不保留暗中的旧语义分支。
- 主控管理工具声明变化后，为各 Bot 安排明确的初始化／续接步骤；已有原生工具清单不会因普通宿主重启自动刷新。是否用私聊 `/new continue` 提炼旧上下文应作为发布操作明确记录。
- 恢复旧版本只能通过一致的备份恢复，不用兼容代码在新旧所有权语义间混跑。

Git 管理：提交领域规则、配置 schema／脱敏示例、迁移工具、命令注册表、测试和本文。真实 Bot 凭据、Principal 映射、群绑定、个人三文件上下文、会话数据库、附件及探针结果留在 `.local` 或用户自己的上下文目录，不进 Git。

后续开发可直接引用本文与 A01–A20。产品主线已有决策，剩余的平台实测门槛明确列在第 10 节；其结果不满足时，应先报告能力缺项并修订设计，不能静默换成另一套群行为。
